# 구현 단위 나누기 · 난이도 분류

구현 단위는 "얼마나 많은 코드인가"가 아니라 **"구현 전에 무엇이 정해져야 하는가"**로 나눈다. 단순 구현처럼 보여도, 전제가 데이터로 확인되지 않았거나 담당자 결정이 필요한 단위가 있다. 그런 단위를 단순 구현으로 다루면 다 만든 뒤에 뒤집힌다.

사용자가 단위 목록을 쓰지 않았으면 등급을 붙인 **초안**을 제시한다. 등급마다 아래 신호표의 근거를 한 줄 붙인다. 형식:

```text
U1: 단위 이름 → 등급(1/2/3) / 관련 R·C 번호 / 왜 그 등급인지 한 줄
```

## 세 등급

| 등급 | 뜻 | 구현 전에 필요한 것 | 결과물 | 진행 |
|---|---|---|---|---|
| **1 단순** | 요구가 확정됐고 방법이 하나로 정해진다 | 없음 | 코드 | 구현 세션에 바로 맡긴다 |
| **2 확인** | 전제가 데이터로 확인되지 않았다 ("기존 노선표를 그대로 써도 되나") | 데이터 확인 카드 | **사실 하나** (코드가 아니다) | 조회는 구현 세션, 결과 해석과 다음 행동은 사용자 |
| **3 결정** | 요구가 담당자 답이나 트레이드오프 선택에 달려 있다 | 꼬리 질문, 선택지, 합의(또는 옵션화) | 결정 기록 → 그다음 코드 | 기록 세션에서 결정 → 구현 세션에서 구현 |

2 확인의 결과에 따라 단위가 3 결정으로 올라가거나 1 단순으로 내려갈 수 있다. 그때 등급을 고치고 결정 로그에 남긴다.

## 점검 — 등급이 낮게 매겨진 단위 찾기

사용자가 쓴 목록이면, 아래 신호가 있는데 1로 매겨진 단위만 짚는다. 초안을 낼 때도 이 신호로 등급을 정한다.

| 신호 | 기록에서 보는 곳 | 시사하는 등급 |
|---|---|---|
| 기존 데이터·자료를 "그대로 쓴다"는 전제 | 요구사항 해석 | 2 |
| 데이터 품질·범위·최신성을 확인한 적 없음 | 증거 칸 비어 있음 | 2 |
| 관련 제약의 톤이 "미지근"이거나 수치가 없음 | 제약 표 | 3 |
| 관련 제약이 다른 제약과 충돌하고 우선순위가 없음 | 제약 표의 충돌 칸 | 3 |
| 관련 요구가 가정(A#)에 기대고 있음 | 요구사항 상태 "가정" | 2 또는 3 |
| 담당자가 "있으면 좋다"며 추가 요구를 꺼냄 | 담당자 질문 표 | 3 |

출력:

| U | 사용자 등급 | 신호 | 시사 등급 | 구현 전에 할 일 |
|---|---|---|---|---|
| U2 | 1 | "기존 노선 그대로" 전제, 확인 기록 없음 | 2 | 데이터 확인 카드 K# 작성 |

## 2 확인 — 데이터 확인 카드

특히 **"결과가 이러면 → 이렇게"** 칸이 비었는지 본다. 분기가 없는 확인은 결과를 봐도 할 일이 정해지지 않는다.

```text
K1 [U2] 확인할 전제: 기존 노선이 현재 거주지를 덮는다
       확인 방법: 정류장별 도보 15분 내 근로자 수 집계
       결과가 이러면 → 이렇게:
         덮지 못하는 사람이 많음 → 노선을 새로 생성 (U3, 등급 3)
         적음 → 기존 노선 유지 + 예외 처리 (등급 1)
```

결과는 사용자가 보고 해석해 카드에 적는다. 그 결과가 담당자에게 보여 줄 근거가 되면 담당자 질문으로 이어 간다("확인해 보니 ___명이 15분 밖입니다. ___로 진행할까요?").

## 3 결정 — 구현 전에 닫을 것

**3으로 분류하는 즉시 입출력 형식부터 정한다.** 그 단위가 무엇을 받아 무엇을 돌려주는지(예: 정류장·근로자 → 노선 목록). 결정이나 실험이 끝나기 전에도 구현 세션이 이 형식의 임시 버전(가짜 결과를 돌려주는 함수)으로 v0를 끝까지 만들 수 있다. 구현 단위 표의 "전제·확인할 것" 칸에 적고, 실험 카드는 이 형식을 그대로 쓴다.

아래가 모두 있어야 실제 구현을 구현 세션으로 넘긴다.
1. 관련 제약과 충돌 쌍 (`interpret.md`의 E)
2. 담당자 답 또는 역제안·옵션화 합의 (`stakeholder.md`)
3. 사용자가 고른 방식과 "어떻게 설명할지" 한 문장 (`design.md`)
4. 결과를 확인할 기준 (`AGREEMENT.md` 성공 기준 번호)

옵션화로 합의했다면, 옵션 값이 바뀌어도 그 단위 안에서만 고치면 되게 만들도록 구현 세션에 전할 한 줄을 사용자에게 제안한다.

## 실험 세션 열기 (필요할 때만)

**열 조건:** 3등급 단위이고, 방식을 한 번에 정할 수 없어 설정을 바꿔 가며 결과를 비교해야 할 때. 그 외에는 열지 않는다. 세션이 늘수록 사람이 오가는 비용이 커진다.

**열기 전에 실험 카드를 만든다**(형식: `records.md`).
- **입출력 형식:** 3으로 분류할 때 정한 형식을 그대로 쓴다. 실험 결과는 이 형식에 맞춰 넘겨야 구현 세션의 임시 버전을 그대로 갈아 끼울 수 있다.
- **작업 폴더:** 실험 세션이 고치는 곳. 세션별로 고치는 파일은 SKILL.md의 "세션 구성"을 따른다.
- **시간 상한, 성공 기준, 상한 도달 시 대안:** 실험은 끝이 없다. 대안은 보통 "가장 나은 버전 + 옵션화로 닫기"이고, 이것이 아래 "닫기"와 "순서"에서 말하는 기본 대안이다.

카드가 차면 실험 세션의 첫 지시를 사용자에게 한 줄로 준다.
> "REQUIREMENTS.md의 실험 카드 X1과 AGREEMENT.md를 읽고, `experiments/routing/`에서만 작업해. 실험마다 EXPERIMENTS.md에 한 줄씩 남기고, 설정별 결과를 비교표로 만들어."

실험 세션이 남길 `EXPERIMENTS.md` 형식(사용자가 실험 세션에 전한다):

```markdown
| # | 시각 | 바꾼 설정 | 결과 수치 (성공 기준별) | 판단 | 코드 위치 |
|---|---|---|---|---|---|
| 1 | 12:10 | 군집 수준 0.5km | 버스 8대, 최대 도보 14분, 최대 우회 1.3배 | 기준 1·2 충족 | experiments/routing/v1.py |
```

## 실험 결과를 결정으로 바꾸기

사용자가 실험 비교표를 기록 세션에 붙여 넣으면:
1. 비교표가 트레이드오프를 보여 주는지 본다. 설정별로 성공 기준 수치가 나란히 있어야 담당자에게 보여 줄 수 있다.
2. 담당자 질문을 다듬는다(`stakeholder.md`의 충돌·옵션화). 예: "이 수준이면 버스 8대에 최대 도보 14분, 저 수준이면 6대에 18분입니다. 어느 쪽으로 할까요? 정하기 어려우시면 직접 고르실 수 있게 하겠습니다."
3. 답을 받으면 합의 표와 실험 카드의 결과 칸에 남기고, 실험 세션에 확정 기준을 전할 한 줄을 사용자에게 준다.

## 실험 세션 닫기

- 확정되면 실험 세션이 결과를 입출력 형식에 맞는 모듈 하나로 정리하고, 구현 세션이 그것을 붙인다.
- 상한에 도달하면 카드의 대안대로 닫고, 남은 한계를 결정 로그에 남긴다(제출 때 HANDOFF.md의 한계점으로 옮겨진다).
- 닫은 시각과 이유를 결정 로그에 "세션 넘김"으로 남기고, 구현 단위 표의 상태를 갱신한다.

## 순서

- **2와 3을 먼저 시작한다.** 담당자 답과 데이터 확인은 기다리는 시간이 있고, 결과에 따라 다른 단위가 바뀐다.
- 기다리는 동안 구현 세션은 1 단순 단위를 진행한다.
- 시간이 부족하면 실험 세션이 없는 3 결정 단위도 기본 대안(옵션화 + 기본값)으로 닫고, 남은 한계를 결정 로그에 남긴다.
