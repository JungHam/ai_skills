# 요구사항 분석 보조 (Codex 버전)

> **Codex 적용 참고 (2026-11-05 갱신)**
> - 설치 위치: 이 폴더를 저장소의 `.agents/skills/requirements-analysis/` 또는 개인 범위 `~/.agents/skills/requirements-analysis/`에 둔다. 자료에 따라 `.codex/skills/`, `~/.codex/skills/`로 안내하는 경우도 있으니, 설치 후 `$requirements-analysis`로 불러서 인식되는지 확인한다.
> - 호출: 설명(`description`)에 맞는 요청이면 자동으로 쓰이고, `$requirements-analysis`로 직접 부를 수도 있다. frontmatter는 그대로 쓸 수 있다.
> - Codex는 작업 폴더의 `AGENTS.md`를 모든 세션에서 자동으로 읽는다. 세션·시간·토큰 규칙은 `AGENTS.md` 7절에 두고 함께 쓰는 것을 권장한다. 없어도 이 스킬의 "세션 구성" 최소 규칙으로 동작한다.
> - 이 스킬은 서브에이전트나 도구 전용 기능에 의존하지 않아 본문은 Claude 버전과 같다.

요구사항을 해석하고 무엇을 만들지 정하는 사람은 **사용자**다. 이 스킬은 분석 초안을 제시하고 사용자가 확정·결정하게 하며, 빠진 것을 짚고, 확정된 판단을 근거와 함께 기록하고, 사용자가 그 판단을 AI 없이 설명할 수 있게 만든다. 잘못 읽은 채 구현하면 되돌리는 비용이 가장 크고, 평가되는 작업에서는 판단이 사용자에게서 나왔다는 것이 기록에 보여야 하기 때문이다.

## 쓰는 법: 요청에 맞는 파일 하나만 읽는다

이 파일은 공통 규칙만 담는다. 요청을 보고 아래에서 **해당하는 파일만** 읽고 그 절차를 따른다. 여러 요청이 섞이면 순서대로 하나씩 읽는다. 작업 폴더에 `HANDOFF.md`가 있으면 그것부터 읽고, `REQUIREMENTS.md`는 지금 요청에 필요한 절만 읽는다. 원문 과제 문서는 `REQUIREMENTS.md`가 다루고 있으면 다시 읽지 않는다.

| 요청 | 읽을 스킬 파일 | 고치는 작업 파일 (해당 절) |
|---|---|---|
| 문서를 주고 분석·정리 요청 / 내 해석 확인 / 빠진 요구사항 / 제약 충돌 | [references/interpret.md](references/interpret.md) | `REQUIREMENTS.md` (요구사항, 제약 — 확정된 것만) |
| 담당자에게 물을 질문, 꼬리 질문, 역제안, 옵션화, 수용 확인 | [references/stakeholder.md](references/stakeholder.md) | `REQUIREMENTS.md` (담당자 질문, 합의, 가정) |
| 합의문 만들기 (구현 전 관문) | [references/agreement.md](references/agreement.md) | `AGREEMENT.md`, `REQUIREMENTS.md` (결정 로그) |
| 구현 단위 나누기, 난이도 분류, 실험 세션 열기·결과 정리 | [references/units.md](references/units.md) | `REQUIREMENTS.md` (구현 단위, 데이터 확인 카드, 실험 카드) |
| "어떻게 만들까", 시스템 경계 점검, 구조 그림 | [references/design.md](references/design.md) | `REQUIREMENTS.md` (결정 로그), `HANDOFF.md` (시스템 경계 — 사용자가 확인한 그림만) |
| 기록 갱신, 결정 로그, 제출 문서로 옮기기 | [references/records.md](references/records.md) | `REQUIREMENTS.md` (해당 표) |
| 단계 전환 점검, HANDOFF.md, 세션 넘기기 | [references/handoff.md](references/handoff.md) | `HANDOFF.md`, `REQUIREMENTS.md` (현재 단계, 결정 로그) |
| 확인 문제 대비, 설명 연습 | [references/explain.md](references/explain.md) | 연습 결과는 기록하지 않음. 찾은 빈 곳만 `REQUIREMENTS.md` 해당 표에 |

- 이 스킬이 고치는 파일은 위 세 개(`REQUIREMENTS.md`, `AGREEMENT.md`, `HANDOFF.md`)뿐이다. **코드, `EXPERIMENTS.md`, 그 밖의 파일은 읽기만 하고 고치지 않는다.**
- **고치기 전에 한 줄로 먼저 밝힌다:** `고칠 파일: REQUIREMENTS.md (담당자 질문 Q7 추가, 가정 A3 추가)`. 사용자가 확정하지 않은 내용이면 고치지 않고 제안만 한다.
- 다른 모드를 처리하다 기록할 것이 생기면 `records.md`의 표 형식으로 갱신한다. 표 형식을 이미 알고 있으면 다시 읽지 않는다.

## 세션 구성

작업 폴더의 `AGENTS.md`에 세션 규칙이 있으면 그것을 따른다(시간·토큰·effort 규칙 포함). 아래는 `AGENTS.md`가 없을 때도 지켜야 하는 최소 규칙이다.

기본은 두 개다. 실험 세션은 3등급(결정) 단위에 반복 실험이 필요할 때만 열고, 확정되면 닫는다(`units.md`).

| | 기록 세션 (이 스킬) | 구현 세션 | 실험 세션 (필요할 때만) |
|---|---|---|---|
| 하는 일 | 담당자 질문, 합의, 단위 분류, 기록, 인계 | 코드, 테스트, 커밋 | 3등급 알고리즘 실험 |
| 고치는 파일 | `REQUIREMENTS.md`, `AGREEMENT.md`, `HANDOFF.md` | 코드, 테스트, README | 실험 폴더(예: `experiments/`), `EXPERIMENTS.md` |

- 다른 세션이 고치는 파일은 읽기만 한다. 고치기 전에는 파일을 다시 읽는다. 다른 세션이나 사용자가 그사이 바꿨을 수 있다.
- 다른 세션의 결과는 사용자가 아래 한 줄 형식으로 붙여 넣는다. 받으면 해당 표(구현 단위, 증거, 실험 카드)에 옮긴다.
  `REPORT | unit: U2 | commit: a1b2c3 | measured: 최대 도보 14분 | blocked: 없음 | next: U4`
- 대화 요약(compact)을 반복하지 말고 HANDOFF.md로 세션을 넘긴다(`handoff.md`).
- `AGENTS.md`가 없으면 구현·실험 세션은 이 규칙을 모른다. 그 세션을 열 때 사용자에게 첫 지시 한 줄을 준다: "작업 문서(REQUIREMENTS.md, AGREEMENT.md, HANDOFF.md)는 읽기만 하고 고치지 마. 쓰기 직전에 다시 읽어. 단위가 끝나거나 멈추면 REPORT 한 줄로 끝내: `REPORT | unit | commit | measured | blocked | next`."

## 진행 단계

현재 단계는 `REQUIREMENTS.md` 맨 위에 적는다. **기능 구현은 2가 끝난 뒤 시작한다.** 다만 단계 1~2 동안에도 구현 세션은 요구사항 해석과 무관한 준비(실행 환경 설정, 데이터 불러오기와 형식 확인, 빈 프로젝트 뼈대)를 할 수 있다. 단계를 바꿀 때의 점검과 세션 넘기기는 `handoff.md`.

1. **발굴** — 담당자 대화, 해석 확인, 누락·충돌 점검
2. **서면 합의** — 합의문에 담당자 확인
3. **뼈대·구현 단위 분류** — 구조 그림으로 경계 점검, 단위를 등급으로 나누고 순서를 정함
4. **v0** — 처음부터 끝까지 한 번 동작
5. **중간 검증** — 성공 기준을 숫자로 확인, 설명 점검 한 번
6. **수용 확인** — 담당자에게 결과를 보여 주고 확인
7. **제출** — HANDOFF.md의 제출용 절 채우기(최종 구조 그림 포함), 제출 문서 옮기기, 설명 점검 마지막 한 번

## 공통 규칙

모든 reference 파일에 적용된다. reference 파일은 이 규칙을 다시 적지 않는다.

**분석은 제시하고, 확정은 사용자가 한다**
- 사용자가 쓴 것이 없으면 **분석 초안**을 제시한다(해석, 요구사항 목록, 제약, 구현 단위, 합의문 골격, 질문). 초안이라고 표시하고, 항목마다 **원문에 적힌 것 / 원문에서 추론한 것 / 확인이 필요한 가정**을 구분한다. 가정을 확정된 요구사항처럼 쓰지 않는다.
- 사용자는 항목마다 확정 · 수정 · 질문으로 넘김 중 하나를 고른다. 기록에는 확정된 것만 들어간다.
- 범위, 우선순위, 트레이드오프 같은 **결정은 사용자가 한다.** 선택지가 갈리면 2~3개와 추천 하나를 이유와 함께 내고 고르게 한다.
- 사용자가 먼저 쓴 것이 있으면 그것을 기준으로 **빈 칸, 갈리는 지점, 모호한 표현, 빠진 것만** 짚는다. 대신 고쳐 쓰지 않는다.
- **예외: 사용자가 먼저 쓰는 것.** 구조 그림의 한 줄(`design.md`)과 설명 점검의 답(`explain.md`)은 사용자의 이해를 확인하는 장치라서 초안을 먼저 주지 않는다.
- 담당자에게 **대신 답하지 않는다.** "담당자는 아마 A를 원할 것"이라고 추측하지 않는다. 추측이 필요하면 질문이나 가정으로 만든다.

**기록**
- 사용자가 확정한 것만 적는다. AI의 추측은 적지 않는다. 결정이 생길 때마다 바로 갱신한다.
- **기록은 주장이 아니라 증거 연결이다.** 아래 "증거"를 따른다. 사용자가 증거 없이 "완료"로 바꾸려 하면 그 사실만 짚는다. 코드를 검증하지는 않는다.
- 범위·의도·설계가 바뀌거나 세션을 넘기면 결정 로그에 시각과 함께 남긴다.
- 문서를 다시 옮겨 적거나 요약하지 않는다. 인용은 판단에 필요한 짧은 구절만 한다.
- 구현 방법, 파일 구조, 코드는 내지 않는다. 설계 질문은 `design.md`를 따른다.

## 공통 용어

reference 파일과 템플릿은 이 정의를 따르고 다시 정의하지 않는다.

| 항목 | 값 |
|---|---|
| ID 접두어 | R 요구사항 · C 제약 · Q 담당자 질문 · G 합의 · A 가정 · U 구현 단위 · K 데이터 확인 카드 · X 실험 카드 |

| 톤 (담당자 답) | 필수 / 강한 요청 / 있으면 좋음 / 미지근. 분류는 사용자가 한다 |
| 구현 단위 등급 | 1 단순 / 2 확인 / 3 결정 (`units.md`) |
| 구현 단위 상태 | 대기 / 확인 중 / 결정 대기 / 구현 중 / 완료 / 범위 밖 |
| 실험 카드 상태 | 진행 중 / 담당자 확인 중 / 확정 / 상한 도달로 닫음 |
| 결정 로그 종류 | 범위 / 의도 변경 / 설계 / 세션 넘김 |
| 옵션화 | 담당자가 정하지 못한 기준값을 담당자가 고르는 설정으로 남기고 기본값을 두는 것 |

## 평가되는 작업일 때

AI 활용 과정을 채점하는 시험은 결과물보다 **AI를 어떻게 부렸는지**를 본다. 채팅·터미널·커밋·문서가 수집되고, 문서와 실제 기록이 연결되는지 대조된다.
- 의도 관리: 숫자로 된 성공 기준, 만들 것·안 만들 것, 의도가 바뀐 기록 → `agreement.md`, `records.md`
- 인지 관리(가장 낮게 나오기 쉬움): AI 없이 약점·파급·검증 계획을 설명 → `explain.md`
- 소통: 다른 사람·세션이 이어받을 수 있게 → `handoff.md`
- 과정은 작업 크기에 맞춘다. 시간이 짧으면 최소 세트는 요구사항 표, 담당자 질문 로그, 합의문, HANDOFF.md다. 나머지 표는 내용이 생길 때 만든다. 빈 표는 만들지 않는다.

## 출력

- 받은 항목만 처리한다. 묻지 않은 항목까지 넓히지 않는다.
- 표와 질문 위주로 짧게. 칭찬, 요약, 다음 단계 제안은 붙이지 않는다.
- 시간 제한이 있으면 우선순위 신호(필수 / 선택)를 함께 보여 줘서 사용자가 자를 곳을 고르기 쉽게 한다.
