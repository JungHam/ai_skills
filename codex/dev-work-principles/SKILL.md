# 개발 작업 원칙 (Codex 버전)

> **Codex 적용 참고 (2026-10-31 확인)**
> - 설치 위치: 이 폴더를 프로젝트 범위는 `.codex/skills/dev-work-principles/`, 개인 범위는 `~/.codex/skills/dev-work-principles/`에 두면 Codex가 `SKILL.md`의 `name`·`description`만 먼저 읽어 자동 호출(implicit invocation) 여부를 판단하고, 쓰기로 결정했을 때 본문 전체를 로드한다 — 아래 frontmatter는 그대로 쓸 수 있다.
> - 원칙 10과 [`references/subagent-review.md`](references/subagent-review.md)의 "서브에이전트"는 Codex의 Subagents 기능에 대응한다: 기본 역할은 `explorer`(읽기 전용)·`worker`(읽기·쓰기)·`default`(범용)이고, 역할별 커스텀 에이전트는 `.codex/agents/*.toml`로 정의한다. 동시 실행 수는 `agents.max_threads`(기본 6), 중첩 깊이는 `agents.max_depth`(기본 1 — 서브에이전트가 또 서브에이전트를 못 낳음)로 제어된다.
> - 나머지 원칙(1~9, 11)은 특정 도구에 매여 있지 않은 일반 지침이라 수정 없이 그대로 적용된다.

사용자와 함께 코드를 만들면서 굳어진 11가지 원칙이다. 각 원칙에는 그렇게 하게 된 계기가 있으니, 규칙을 기계적으로 적용하기보다 **왜**를 이해하고 상황에 맞게 판단한다. 예시는 흔한 상황(결제 API 연동, 주문 내보내기, 예약 작업, 웹 폼)에서 골랐다. 실제 프로젝트의 언어·프레임워크에 맞게 바꿔 적용한다.

작업 흐름은 대체로 이렇다.

```
요청 → (크면) 쪼개기 → 계획 [→ 계획 검토 서브에이전트(요청 시)] → 계획 제시·확인
     → 구현(모듈화·가독성) → 테스트(우선순위·edge case) [→ 결함 주입 서브에이전트]
     → 실제 동작 검증(캡처·시뮬레이션) → 마크다운 검증 보고서 [→ 보고서 감사 서브에이전트]
         ↑ 이 모든 단계에서: 보안 데이터 비유출, 근거 없는 추가 금지, 질문에는 대안+이유,
           사용자가 골라야 하는 결정은 결정 기록 문서
         [ ] 안은 원칙 10의 조건에 걸릴 때만. 계획 검토는 사용자가 요청할 때만
```

## 1. 보안 데이터는 어떤 경우에도 밖으로 내보내지 않는다

API 키·앱 비밀번호·토큰은 **값 자체가 대화, 로그, 예외 메시지, 커밋, 외부 서비스로 나가지 않게** 한다. 흔한 사고 경로가 있다: API 키를 쿼리 파라미터로 보내는 API에서 요청이 실패하면, HTTP 라이브러리가 만든 오류 메시지에 **키가 들어간 요청 URL**이 그대로 실려 로그와 알림 메일로 퍼진다. 그래서 비밀값을 가리는 함수(예: `mask_secret(text)`)를 한곳에 두고, 외부 호출을 감싸는 공통 함수에서 오류 메시지를 가린다.

- `.env`나 비밀 설정 파일은 **값을 출력하지 않는다.** 필요한 건 "변수가 있는가 / 비어 있지 않은가 / 형식이 맞는가"뿐이다. 키 동작 테스트도 응답 코드만 보고하고 키는 마스킹한다.
  ```bash
  # 좋음: 존재 여부만
  grep -c '^PAYMENT_API_KEY=.\+' .env
  # 나쁨: cat .env, echo $PAYMENT_API_KEY, 환경 변수 전체 출력(print(os.environ), console.log(process.env))
  ```
- 오류를 감싸 다시 던질 때는 **원인 체인**에도 비밀값이 남는다(Python `__cause__`/`__context__`, JavaScript `error.cause`, Java `getCause()`). 체인 출력만 끊는 방법(Python `raise ... from None` 등)은 원래 오류 객체에 붙은 요청 URL을 지우지 못한다. 근본 처리는 **메시지와 URL 자체를 마스킹한 새 오류**를 만드는 것이다.
- 비밀값을 URL 쿼리, 웹 폼, 외부 API, 문서 초안, 캡처 화면에 넣지 않는다. 캡처 전에 화면에 키·이메일 주소가 보이면 가리거나 다른 화면을 쓴다.
- **고유 식별 정보**(이메일 주소, 전화번호, 계정 ID, 차량 번호처럼 사람이나 기기를 특정할 수 있는 값)는 다루기 전에 사용자에게 확인한다: 어디에 쓸지, 저장해도 되는지, 마스킹할지. 예: 알림 메일 수신자를 코드에 하드코딩하지 않고 환경 변수로 둘지 묻는다.
- 비밀값을 넣거나 바꾸는 작업(`.env` 수정 등)은 사용자가 직접 하도록 변수 **이름**만 알려 준다. ("메일 발송용 앱 비밀번호를 쓸 거야. 환경 변수 이름 알려줘" → `ALERT_SMTP_PASSWORD`처럼 이름만 제시)
- 사용자가 요청해도 비밀값을 화면에 출력하거나 외부로 보내야 하는 상황이면, 멈추고 왜 위험한지 설명한 뒤 대안(마스킹 출력, 앞 4자리만 표시 등)을 제시한다.

## 2. 한 번에 처리하기 어려운 요청은 하위 단위로 쪼개게 유도한다

다음 중 하나라도 해당하면 바로 손대지 않고 쪼갠다.
- 서로 다른 파일·모듈 3개 이상을 동시에 바꿔야 한다.
- 결과를 한 번에 검증할 수 없다(테스트·캡처 하나로 "됐다"를 말할 수 없다).
- 사용자가 내려야 할 결정이 2개 이상 섞여 있다.
- 예상 작업량이 90분을 넘는다.

쪼갤 때는 **각 단위가 혼자서 완료·검증 가능**하게 만든다. 형식:

```markdown
"주문 내역을 CSV로 내려받는 기능"은 한 번에 하기엔 커서 이렇게 나누면 좋겠어요.
| 단위 | 하는 일 | 완료 기준(무엇으로 확인) | 예상 |
|---|---|---|---|
| U1 | 주문 목록 → CSV 문자열 변환 함수 | 빈 목록·쉼표 든 상품명·날짜 형식 테스트 통과 | 40분 |
| U2 | 다운로드 API 엔드포인트 | 실제 서버에 요청해 파일이 내려옴 | 30분 |
| U3 | 화면의 "내려받기" 버튼 | 브라우저에서 클릭 → 파일 저장 캡처 | 40분 |
U1부터 시작할까요?
```

사용자가 이미 단위를 나눠 두었다면(작업 목록·이슈·체크리스트) 그 단위를 그대로 따른다.

## 3. 테스트 통과 ≠ 기능 검증 완료. 동작하는 화면을 증거로 남긴다

단위 테스트는 "내가 상상한 입력"에서만 맞다는 걸 보여 준다. UI/UX, 사용자 상호작용, 예약·배치 작업처럼 **실제 런타임에서 동작이 드러나는 기능**은 테스트 통과 후에도 실제로 돌려 보고 증거를 남긴다. 예: 예약 작업이 테스트에서는 "예약 시각" 값을 항상 받았지만, 운영 중 **수동 실행**하자 그 값이 비어 있어 실제 실행에서 깨지는 일. 웹 폼이 단위 테스트는 다 통과했지만, 저장 응답을 기다리는 사이 사용자가 입력한 글자를 지워 버리는 일.

- 검증 대상과 방법:
  - 웹 화면: 브라우저 자동화(Playwright, Cypress 등)나 브라우저 도구로 클릭·입력을 시뮬레이션
  - 모바일 앱: 시뮬레이터·에뮬레이터 화면
  - 예약·배치 작업: 스케줄러의 실행 기록 화면(cron 로그, CI 작업 기록, 워크플로 도구 UI 등)과 재시도 횟수
  - 알림: 실제로 받은 메일·메신저 메시지
  - 파일·저장소 결과: 실행 전후 파일·행 수 비교
  - CLI: 명령 출력
- 캡처는 **검증한 기능이 이름에 드러나게** 짓는다: `{기능}_{시나리오}_{결과}.png`, 소문자·스네이크 케이스.
  - 좋음: `todo_add_two_then_listed.png`, `retry_job_4_attempts_then_failed.png`, `daily_import_rerun_same_row_count.png`, `failure_email_received_masked_key.png`
  - 나쁨: `screenshot1.png`, `캡처.png`, `image (3).png`
- 실패 경로도 캡처한다. "정상 동작"만큼 "의도대로 실패함"이 중요하다.
- 캡처에 비밀값·식별 정보가 보이면 원칙 1을 따른다.
- 보고서는 **마크다운**으로, 캡처는 **상대 경로 하이퍼링크**로 남긴다. 서식은 [`references/verification-report.md`](references/verification-report.md)를 따른다. 저장 위치는 별도 지시가 없으면 작업 중인 프로젝트의 `docs/verification/YYYY-MM-DD_{기능}.md`, 캡처는 같은 폴더의 `captures/`.
- 사람 눈으로만 확인할 수 있는 단계(메일 수신 등)는 사용자에게 확인을 부탁하고, 사용자가 말한 관찰 결과를 원문 그대로 보고서에 적는다. 직접 확인하지 못한 것은 "확인됨"이라고 쓰지 않는다.
- 보고서를 사용자에게 넘기기 전에 원칙 10의 **보고서 감사**를 거친다. 작성자가 자기 보고서의 ✅를 판정하면 관대해지기 때문이다.

## 4. 테스트는 edge case를 포함해 보수적으로, 반드시 기능을 검증하게 쓴다

상세 체크리스트는 [`references/testing.md`](references/testing.md). 핵심:

- **우선순위 먼저.** 무엇이 깨지면 가장 아픈지(데이터 손실, 멱등성, 재시도를 일으키는 예외, 비밀값 유출)로 순위를 매기고 높은 것만 먼저 구현한다. 보류한 항목은 목록으로 알려 주고 사용자가 고르면 추가한다. 한 번에 많이 만들면 검토 부담이 커지고 약한 테스트가 섞이기 때문이다.
- **edge case를 반드시 고려한다:** 빈 응답, 경계 시각(자정, UTC와 로컬 시간대의 날짜가 다른 시각), 값이 없는 입력(`null`/`None`/`undefined`, 수동 실행 시 비는 값), 중복 실행(멱등성), 부분 실패, 잘못된 자격 증명, 페이지 잘림.
- **모든 테스트 함수 안에서 기능 검증(assert)이 일어나야 한다.** "예외 없이 돌았다"는 검증이 아니다. 반환값·저장된 내용·호출 인자·로그에 비밀값이 없음 등 **관찰 가능한 결과**를 단언한다.
- **보수적으로:** 한 테스트는 한 동작만 본다. 기대값은 구체적인 값으로 쓴다(`== 24`, `> 0` 아님). 외부 API는 실제로 호출하지 않고 모킹한다. 시간은 고정한다.
- **테스트가 결함을 잡는지 확인한다:** 구현을 일부러 깨뜨려 테스트가 실패하는지 본다. 작업 단위에 "높음" 테스트가 있으면 깨뜨릴 곳은 테스트를 쓰지 않은 서브에이전트가 고른다(원칙 10). 테스트를 쓴 쪽은 자기 테스트가 잡을 줄 아는 결함만 넣기 쉽다.
- 기존 테스트와 겹치는 테스트는 만들지 않고, 겹치면 지운다.
- 테스트의 기대값이 도메인 사실(예: "시간별 데이터는 날짜와 상관없이 하루 24행")과 맞는지 확신이 없으면 추측하지 말고 사용자에게 묻거나 문서를 확인한다.

## 5. 모듈화를 기반으로 작업하고, 중복은 함수로 뺀다

- 새 코드를 쓰기 전에 프로젝트에 이미 있는 함수부터 찾는다(공통 HTTP 호출, 비밀값 마스킹, 시간대 변환, 로깅 설정 같은 것). 있으면 재사용한다.
- 같은 로직이 두 곳 이상 나오면 함수로 뺀다. 어디에 둘지는 **책임**으로 정한다: 여러 외부 API에 공통이면 공통 모듈(예: `http_client`), 응답 형태가 API마다 다르면 각 API 모듈(예: `payment_client`, `shipping_client`). 판단이 갈리면 원칙 8대로 대안과 이유를 제시한다.
- 오류는 의미 단위로 계층을 만든다(예: `PaymentApiError` ← `InvalidApiKeyError`). 호출부가 잡아야 할 단위로 나눈다.
- 진입점(라우트 핸들러, CLI 명령, 스케줄러 작업 정의, UI 이벤트 핸들러)은 얇게 유지하고 로직은 별도 모듈에 둔다. 실험용 코드처럼 일회성이라고 사용자가 정한 코드는 그 결정을 존중한다.
- 다만 "언젠가 쓸 것 같은" 추상화는 만들지 않는다. 실제로 중복이 생겼을 때 뺀다. 판단 기준은 원칙 11.

## 6. 코드는 사람이 읽기 쉽게 쓴다. 짧은 게 답이 아니다

- 이름이 의도를 말하게 한다: `next_run_after`, `save_daily_report`, `ImportFailedError`, `isSaving`. 한 글자 변수, 약어(`res2`, `tmp_d`)를 피한다.
- 한 줄에 여러 일을 욱여넣는 컴프리헨션·삼항·체이닝보다, 단계가 보이는 몇 줄을 택한다.
- 매직 넘버는 이름 있는 상수로(`MAX_RETRY_COUNT`, `DEFAULT_PAGE_SIZE`).
- 주석은 **왜**를 쓴다. 무엇을 하는지는 코드가 말한다. 주변 코드의 주석 밀도와 스타일을 따른다.
- 사용자가 처음 볼 만한 문법(오류 체인 끊기, 오류 객체를 동적으로 다시 만드는 코드, 복잡한 제네릭 등)을 쓸 때는 쓰는 이유를 한두 줄로 설명하거나 더 평범한 형태를 고려한다.
- 사용자가 작업 중간에 직접 코드를 고칠 수 있다. 편집 전에는 **항상 현재 파일을 다시 읽고**, 사용자가 고친 부분을 되돌리지 않는다.

## 7. 구현 전에 계획을 먼저 세운다. 요청을 받자마자 코드부터 쓰지 않는다

"구현하자", "~를 수정하자" 같은 요청에도 먼저 계획을 보여 주고 확인을 받는다. 계획에 넣을 것:

```markdown
## 계획: 주문 내보내기(export_orders) 수정
- 목표 / 완료 기준: (무엇이 되면 끝인가, 무엇으로 확인하나)
- 현재 상태: (관련 파일·함수, 지금 어떻게 동작하나 — 읽고 확인한 사실만)
- 변경 내용: 파일별로 무엇을 바꾸나 — 항목마다 근거(요청·중복·관찰·제약 중 무엇, 가리킬 대상)를 함께 (원칙 11)
- 재사용할 기존 함수 / 새로 뺄 함수
- 테스트: 우선순위 높은 것 N개 (보류 목록 별도)
- 실제 동작 검증: 무엇을 돌려 무엇을 캡처하나
- 결정이 필요한 것: (있으면 원칙 8의 형식으로)
```

예외: 오타·한 줄 수정처럼 계획이 곧 변경인 경우, 또는 사용자가 "바로 해줘"라고 명시한 경우. 이때도 무엇을 바꿨는지는 알린다.

사용자가 요청하면("계획 검토해줘", "서브에이전트로 계획 봐줘") 계획을 확정하기 전에 원칙 10의 **계획 검토**를 돌리고, 검토 지적과 반영 여부를 계획 아래에 함께 보여 준다. 작업이 커도 요청 없이 자동으로 돌리지 않는다. 계획은 사용자가 직접 확인하기 때문이다.

## 8. 설계·구현 중 추가 정보 요청에는 상황에 맞는 대안과 이유를 준다

사용자가 "어떻게 해야 해?", "더 안전하게 하려면?", "어디에 두는 게 맞아?"처럼 물으면 정답 하나만 던지지 않는다.

- **현재 상황을 기준으로** 2~3개 대안을 낸다. 일반론이 아니라 그 프로젝트의 제약에 비춰 본다. 확인할 제약의 예: 운영 인원(혼자인가 팀인가), 디스크·비용 한도, 외부 API가 과거 데이터를 다시 조회할 수 있는가, 시간대 기준, 배포 환경.
- 각 대안의 장단점과 **이 상황에서 왜 맞는지/안 맞는지**를 쓰고, 추천 하나를 이유와 함께 고른다. 결정은 사용자에게 맡긴다.
- 사실 주장(라이브러리 동작, 프레임워크 기본값, 외부 API의 갱신 주기)은 기억이 아니라 공식 문서나 실제 코드·로그로 확인하고, 문서에 있는 것 / 없는 것 / 내 추론을 구분해 말한다.

```markdown
| 대안 | 방법 | 장점 | 단점 | 이 상황에 맞나 |
|---|---|---|---|---|
| 1 | 오류 체인 출력만 끊기 | 간단 | 원래 오류 객체의 요청 URL에 키 남음 | 부분적 |
| 2 | 메시지·URL 마스킹한 새 오류 생성 | 근본 차단 | 코드 조금 늘어남 | **추천** — 키 유출 경로를 원천 차단 |
| 3 | 로깅 필터로만 마스킹 | 기존 코드 무변경 | 로그 밖(오류 객체, 메일)은 못 막음 | 보조 수단 |
```

선택지를 내고 사용자가 골라야 하는 상황이면 원칙 9로 결정 기록을 남긴다.

## 9. 사용자가 여러 선택지 중에 골라야 하는 결정은 결정 기록 문서로 남긴다

대화 속 대안 표는 대화가 끝나면 찾기 어렵다. 나중에 "왜 이렇게 했지?"라는 질문에 답하려면 **어떤 대안이 있었고, 누가 무엇을 왜 골랐고, 무엇을 감수했는지**가 문서로 남아 있어야 한다. 회고·리뷰·설계 문서(ADR 등)를 쓸 때 근거가 된다. 서식은 [`references/decision-record.md`](references/decision-record.md).

- **언제 쓰나:** 서로 다른 결과를 낳는 대안을 2개 이상 제시했고, 사용자가 골라야 하는 경우. 원칙 8의 대안 표를 낸 경우는 모두 해당한다. 버그 수정 방식, 기술 선택, 범위·우선순위 결정도 포함한다.
- **쓰지 않는 경우:** 제안이 하나뿐이고 사용자가 승인만 하는 경우("계획대로 시작할까요?" → "응"), 이름·서식처럼 되돌리기 쉬운 사소한 선택.
- **언제 만드나:** 선택지를 제시하는 시점에 `상태: 결정 대기`로 만들고, 대화에는 선택지와 함께 문서 링크를 준다. 사용자가 고르면 같은 문서에 결과를 채우고 `상태: 결정됨`으로 바꾼다. 대화가 중간에 끊겨도 선택지가 남게 하기 위해서다.
- **사용자의 선택과 이유는 원문 그대로 적는다.** 사용자가 이유를 말하지 않았으면 지어내지 않고 "이유는 밝히지 않음"이라고 쓴 뒤, 제안 때의 추천 이유를 따로 적는다. 추천과 다른 대안을 골랐으면 그 사실도 적는다.
- **감수한 단점**과 **다시 볼 조건**을 꼭 적는다(예: "저장이 1초 이상 걸리면 A2 재검토").
- 결정한 뒤 구현·검증이 끝나면 검증 보고서, 테스트 이름, 커밋을 `관련 증거`에 링크한다. 검증 보고서에서도 이 문서를 링크한다.
- **결정을 바꿀 때는 기존 문서를 지우거나 고쳐 쓰지 않는다.** 새 문서를 만들고, 기존 문서는 `상태: 대체됨 → (새 문서 링크)`로 바꾼다.
- **위치:** 작업 중인 프로젝트의 `docs/decisions/YYYY-MM-DD_{주제}.md`. 주제는 영문 소문자·스네이크 케이스(예: `2026-10-30_double_submit_prevention.md`).
  - 프로젝트에 이미 ADR 같은 번호 체계가 있으면 임의로 새 번호를 만들지 않는다. 이 문서를 그 체계에 넣을지 사용자에게 묻고, 관련 ADR이 있으면 근거로 링크한다.
- 결정 하나에 문서 하나를 쓴다. 한 번에 여러 결정을 물었으면 결정마다 따로 만든다.

## 10. 만든 쪽이 스스로 채점하면 관대해진다. 독립 검증은 서브에이전트에게 맡긴다

작성자가 자기 결과물을 판정하는 지점이 세 곳 있다. 계획을 세운 쪽이 빠진 것을 찾고(원칙 7), 테스트를 쓴 쪽이 깨뜨릴 곳을 고르고(원칙 4), 보고서를 쓴 쪽이 "확인됨"을 판정한다(원칙 3). 작성자는 자기가 고려하지 않은 것을 모르므로, 이 세 지점은 **과정을 모르는 서브에이전트가 결과물만 보고** 판정한다.

| 검토 | 언제 돌리나 | 상한 |
|---|---|---|
| 계획 검토 | **사용자가 요청할 때만.** 계획을 확정하기 전 | 요청 1번에 1회 |
| 결함 주입 | 원칙 2의 작업 단위에 "높음" 테스트가 있고 처음 모두 통과했을 때 | 작업 단위당 1회, 결함 최대 5개 |
| 보고서 감사 | 검증 보고서를 만들었을 때. 사용자에게 보고하기 전 | 보고서당 2회(최초 + 재감사 1회) |

**서브에이전트를 띄우기 전에 반드시 [`references/subagent-review.md`](references/subagent-review.md)를 읽는다.** 넘길 것과 숨길 것, 대상 범위(git이 없을 때 포함), 지시문 템플릿, 결과 처리가 거기 있다. 어떤 경우에도 지키는 네 가지:

- 지시문에 무엇을 왜 고쳤는지 흘리지 않는다. 템플릿 문구를 쓰고 경로만 바꾼다.
- 모든 지시문에 원칙 1의 보안 규칙 블록을 넣는다. 서브에이전트는 이 스킬을 읽지 않고 시작한다.
- 결과는 요약하지 않고 원문 그대로 붙이며, 반영하지 않은 지적도 지우지 않는다.
- 조건에 걸리지 않으면 돌리지 않고, 상한에 닿으면 다시 띄우지 않는다. 결함 주입도 테스트처럼 과하게 하지 않는다.

## 11. 오버엔지니어링은 하지 않는다. 판단 기준은 "지금 댈 수 있는 근거"다

느낌으로 판단하면 사람마다, 날마다 달라진다. 그래서 무엇을 **추가할 때마다** 근거를 댈 수 있는지로 판단한다. 대상은 함수·클래스·인터페이스·계층, 설정 옵션·매개변수·플래그, 예외 클래스, 의존성(라이브러리), 캐시·큐·비동기·재시도 같은 인프라, 그리고 테스트·결함 주입·문서까지 포함한다.

**인정되는 근거는 네 가지다.** 하나 이상을 구체적인 대상으로 가리킬 수 있어야 한다.

| 근거 | 가리킬 대상 | 예 |
|---|---|---|
| 요청 | 사용자 요청·완료 기준의 항목, 사용자가 명시한 확장 | "CSV로 내려받기" → CSV 변환 함수 / "나중에 JSON도 넣을 거라 구조를 열어 둬" → 형식 분리 |
| 중복 | 지금 같은 로직이 쓰이는 **두 곳 이상의 실제 위치** | 결제·배송 클라이언트 양쪽의 오류 마스킹 → `mask_secret` |
| 관찰 | 실제로 본 문제: 로그, 재현 결과, 실패한 테스트, 측정값 | 저장 응답 1.2초 측정 → 저장 중 버튼 잠금 |
| 제약·알려진 위험 | 원칙 8에서 확인한 제약, 테스트 우선순위 "높음" 범주(데이터 손실·멱등성·비밀값·재시도/실패 판단) | 예약 작업 재실행 가능 → 멱등 키 |

"나중에 필요할 수도", "확장성", "보통 이렇게 한다", "더 깔끔하다"는 근거가 아니다.

- **계획 단계에서 거른다.** 원칙 7의 "변경 내용" 항목마다 근거 종류와 가리킬 대상을 적는다. 근거를 적지 못하는 항목은 계획에서 뺀다.
- **구현 후에는 지워 본다.** 이 요소를 지우거나 가장 단순한 형태(직접 호출, 상수, 함수 하나)로 바꿔도 완료 기준과 "높음" 테스트가 모두 통과하고, 위 근거 중 어느 것도 깨지지 않으면 과한 것이다. 결함 주입에서 "깨뜨려도 아무 테스트도 실패하지 않는 코드"가 나왔을 때도 같은 질문을 한다: 테스트가 없는 건가, 코드가 필요 없는 건가.
- **자주 나오는 신호.** 보이면 근거를 다시 확인한다.
  - 구현체가 하나뿐인 인터페이스·추상 클래스·전략/팩토리 패턴
  - 기본값 말고 쓰는 곳이 없는 설정 옵션·매개변수·플래그
  - 따로 잡는 곳이 없는 예외 클래스(원칙 5: 호출부가 잡아야 할 단위로만 나눈다)
  - 다른 함수를 그대로 부르기만 하는 래퍼·계층
  - 요청은 한 가지인데 여러 경우를 받도록 일반화한 구조(CSV 요청에 형식 플러그인 구조)
  - 몇십 줄로 될 일에 들인 새 의존성
  - 측정된 문제 없이 넣은 캐시·비동기·큐·재시도
  - 기능보다 커진 테스트·결함 주입·문서
- **애매하면 혼자 정하지 않는다.** "지금 단순하게"와 "미리 대비"가 둘 다 말이 되면 원칙 8의 대안 표로 낸다. 단순한 쪽을 고르면 결정 기록(원칙 9)의 "다시 볼 조건"에 확장이 필요해지는 조건을 적는다. 미래 대비를 코드가 아니라 기록으로 남기는 것이다.
- **이 원칙을 이유로 빼면 안 되는 것:** 원칙 1의 비밀값 보호, 데이터 손실·멱등성 방어, 이미 두 곳 이상에 생긴 중복의 제거. 관찰된 사고가 없어도 "제약·알려진 위험"이나 "중복"이라는 근거가 있다.

## 작업을 마칠 때 점검

- [ ] 출력·로그·커밋·캡처에 비밀값이나 확인받지 않은 식별 정보가 없다
- [ ] 계획을 먼저 보여 주고 확인받았다(또는 예외 사유가 있다)
- [ ] 중복 로직을 기존 함수로 재사용하거나 함수로 뺐다
- [ ] 추가한 함수·옵션·계층·의존성마다 근거(요청·중복·관찰·제약)를 가리킬 수 있다
- [ ] 테스트는 우선순위 높은 것부터, 모든 함수에 의미 있는 assert, edge case 포함, 일부러 깨서 실패 확인
