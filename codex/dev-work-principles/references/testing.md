# 테스트 작성 체크리스트

SKILL.md 원칙 4의 상세판. 테스트를 쓰기 전에 0→1→2→3 순서로 정하고, 다 쓴 뒤 4로 점검한다.

## 0. 과하게 만들지 않는다

테스트도 원칙 11의 추가 대상이다. 근거 없이 늘리면 읽고 고칠 코드만 많아지고, 결과도 길어져 정작 중요한 실패가 묻힌다.

- **완료 기준과 "높음" 위험 하나당 테스트 하나로 시작한다.** 구현 단위당 테스트 함수 5개 안팎이 기준이다. 넘으면 새로 막는 위험이 무엇인지 계획에 적는다.
- **같은 동작은 가장 싼 층 한 곳에서만 확인한다.** 단위 테스트에서 본 입력 검증을 API·E2E에서 다시 보지 않는다. E2E는 핵심 흐름 하나와 화면에서만 드러나는 동작에만 쓴다.
- **입력만 다른 경우는 매개변수화로 묶는다.** 테스트 함수를 복사하지 않는다.
- **프레임워크·라이브러리가 이미 보장하는 동작은 테스트하지 않는다.** 직접 짠 로직만 본다.
- **edge case는 고려하되 전부 구현하지 않는다.** 아래 §2 목록은 빠진 것을 찾는 용도다. 이 기능에서 실제로 일어날 수 있고, 깨지면 아픈 것만 구현한다.
- **버그 하나에 회귀 테스트 하나.** 수정 전 코드에서 실패하는지 확인하고 끝낸다.
- **실행은 필요한 만큼만.** 작업 중에는 바꾼 범위의 테스트만 돌리고, 전체 테스트는 단위가 끝날 때 한 번 돌린다. 같은 코드를 안정성 확인 목적으로 반복 실행하지 않는다. 간헐 실패가 실제로 의심될 때만 반복한다.
- **일부러 깨뜨리기는 메인이 "높음" 테스트에 한해 직접 한다.** 복사본에서 하고, 보고서에 `자체 점검 — 독립 검증 아님`이라고 적는다. 사용자가 서브에이전트 결함 주입을 요청했으면 메인이 따로 깨뜨려 보지 않는다.

### 결과는 간결하게

- 테스트 결과는 `N passed` 같은 한 줄과, 실패가 있으면 실패한 테스트 이름만 남긴다. 전체 출력을 보고서나 대화에 붙이지 않는다.
- 저장 위치와 서식은 [`verification-report.md`](verification-report.md)를 따른다.

## 1. 우선순위 매기기

후보를 모두 적고 "이게 깨지면 무엇을 잃나"로 분류한다.

| 순위 | 기준 | 예 |
|---|---|---|
| 높음 | 데이터 손실·오염, 멱등성 붕괴, 비밀값 유출, 재시도/실패 판단을 바꾸는 예외 | 같은 날짜로 가져오기 작업을 다시 돌려도 행 수가 그대로, 잘못된 API 키면 `InvalidApiKeyError`가 나고 메시지에 키가 없음, 일부 항목만 실패하면 실패한 항목만 모아서 보고 |
| 중간 | 경계 조건에서 잘못된 값 저장 | 자정 직전·직후 주문이 다른 날짜 파일로 들어감, 페이지 잘림 경고 |
| 낮음 | 로그 문구, 보조 유틸의 사소한 분기 | 로그 메시지 형식 |

**높음만 먼저 구현**하고, 나머지는 이렇게 알린다. 한 번에 많이 만들면 검토 부담이 커지고 약한 테스트가 섞이기 때문이다.

```markdown
먼저 구현한 테스트(높음): 3개 — ...
보류한 테스트(중간/낮음):
- [중간] 23:59→00:00 경계에서 날짜 파티션 값
- [낮음] 잘림 경고 로그 문구
추가할 항목을 골라 주세요.
```

## 2. edge case 목록 (해당하는 것만 고른다)

- **빈 값**: 빈 응답(목록이 `""`/`[]`/`null`), 빈 입력 문자열, 공백만 있는 문자열
- **경계 시각**: 자정, 구간 경계(04:59 → 05:00), UTC와 로컬 시간대의 날짜가 다른 시각
- **값 없음**: `null`/`None`/`undefined`, 선택 인자 미지정, 수동 실행 시 비는 값(예: 예약 실행 시각)
- **반복 실행**: 같은 입력 2~3회 → 결과 동일(멱등성)
- **부분 실패**: 일부 항목만 실패 → 실패한 것만 보고·재시도
- **잘못된 자격 증명**: 미등록 키, 만료 키 → 올바른 예외 + 비밀값 미노출
- **외부 응답 이상**: 4xx/5xx, 타임아웃, 성공 코드인데 본문이 오류 형식, 페이지 잘림(전체 건수 > 한 페이지 크기)
- **타입 변형**: 숫자/문자열 혼재(`100` vs `"100"`)
- **화면 동작**: 빠른 연속 클릭·Enter 연타, 응답을 기다리는 사이의 입력, 사용자 입력에 든 HTML 태그

## 3. 테스트 함수 작성 규칙

- **함수마다 기능을 검증하는 assert가 있어야 한다.** 아래는 검증이 아니다.
  ```python
  def test_export_runs():
      export_orders(date(2026, 10, 22))   # 예외만 안 나면 통과 → 아무것도 검증 안 함
  ```
  관찰 가능한 결과를 단언한다.
  ```python
  def test_export_orders_writes_header_and_one_row_per_order(tmp_path, two_orders):
      path = export_orders(date(2026, 10, 22), out_dir=tmp_path)
      lines = path.read_text().splitlines()
      assert lines[0] == "order_id,ordered_at,amount"
      assert len(lines) == 1 + 2
  ```
  ```javascript
  test("exportOrders writes header and one row per order", async () => {
    const csv = await exportOrders(twoOrders);
    const lines = csv.split("\n");
    expect(lines[0]).toBe("order_id,ordered_at,amount");
    expect(lines).toHaveLength(1 + 2);
  });
  ```
- 한 테스트 = 한 동작. 이름은 `{대상}_{조건}_{기대 결과}` 순서로 읽히게.
- 기대값은 구체적으로(`== 24`, `== "dt=2026-10-22"`). `is not None`, `> 0`만으로 끝내지 않는다.
- 예외 테스트는 타입과 핵심 내용을 함께 본다: 예외 타입 + 메시지에 키 원문이 없음.
- 외부 API·메일 발송은 모킹한다. 실제 호출은 원칙 3의 실제 동작 검증에서 한다.
- 시간은 고정한다. 현재 시각을 인자나 생성자로 주입받게 만들고, 테스트에서 고정값을 넣는다. 고정 시각은 **서로 다른 구간에서 두 개 이상** 쓴다. 하나만 쓰면 테스트를 실제로 돌리는 시각이 우연히 같은 구간일 때, 주입된 시각을 무시하는 버그도 통과한다.
- 성공 경로만 보는 테스트, 구현 세부(내부 임시 파일 이름 등)에 묶인 테스트는 약한 테스트다. 동작을 보는 형태로 바꾼다.
- 반복되는 준비 코드는 fixture·헬퍼로 뺀다(원칙 5). 기대 문구 같은 값은 앱 코드의 상수를 가져다 쓰지 말고 테스트에 직접 적는다. 앱 상수를 쓰면 상수가 잘못 바뀌어도 테스트가 함께 바뀌어 잡지 못한다.
- 화면 테스트에서 "두 번째 요청이 나가지 않았다"처럼 **일어나지 않음**을 확인할 때는, 우연한 타이밍에 기대지 말고 요청을 붙잡아 두는 기능(예: Playwright `page.route`, Cypress `cy.intercept`)으로 상황을 고정한다.

## 4. 다 쓴 뒤 점검

- [ ] 구현을 일부러 깨뜨렸을 때(예: 마스킹 줄 주석 처리, 멱등 키에 현재 시각 사용) 해당 테스트가 실패한다. "높음" 테스트에 한해 메인이 확인한다. 서브에이전트 결함 주입은 사용자가 요청할 때만 한다([`subagent-review.md`](subagent-review.md))
- [ ] 깨뜨려도 **아무 테스트도 실패하지 않는 코드**가 있으면, 그 코드를 검증하는 테스트가 없다는 뜻이다. 테스트를 추가하거나, 정말 필요 없는 코드인지 확인한다
- [ ] 기존 테스트와 겹치는 것이 없다(겹치면 지운다)
- [ ] 기대값이 도메인 사실(예: "시간별 데이터는 날짜와 상관없이 하루 24행")과 맞는다 — 불확실하면 추측하지 말고 사용자에게 묻거나 문서를 확인한다
- [ ] 테스트 이름만 읽어도 무엇을 보장하는지 알 수 있다
- [ ] 테스트 실행 결과(통과/실패 수)를 그대로 한 줄로 보고했다. 간헐 실패가 의심돼 반복했다면 횟수도 적었다
- [ ] 각 테스트가 어떤 완료 기준이나 위험을 막는지 말할 수 있다. 말할 수 없는 테스트는 지운다
