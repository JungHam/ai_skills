# 서브에이전트 독립 검토

SKILL.md 원칙 10의 상세판. 계획 검토·결함 주입·보고서 감사를 서브에이전트에게 맡길 때의 조건, 넘길 것, 상한, 지시문 템플릿, 결과 처리를 담는다.

## 언제, 무엇을 넘기나

| 검토 | 언제 돌리나 | 넘길 것 | 넘기지 않을 것 |
|---|---|---|---|
| 계획 검토 | **사용자가 요청할 때만.** 계획을 확정하기 전 | 사용자 요청 원문, 계획서, 확인된 제약 | 계획을 세운 추론, 버린 대안의 이유 |
| 결함 주입 | 원칙 2의 작업 단위마다 최대 한 번. 그 단위에 "높음" 테스트가 있고 처음 모두 통과했을 때 | 이번 단위에서 바뀐 범위(파일·함수 이름), 관련 테스트 파일 경로, 테스트 실행 명령 | 테스트 의도, 우선순위 표, "여기가 약할 것 같다"는 힌트 |
| 보고서 감사 | 검증 보고서를 만든 작업. 사용자에게 보고하기 전 | 보고서 파일, `captures/` 경로 | 구현 과정, 작업 중 대화, 무엇을 고쳤는지 |

- **조건에 걸리지 않으면 돌리지 않는다.** 오타, 한 줄 수정, 원칙 7의 예외에 해당하는 작업에는 비용만 든다.
- **서브에이전트를 쓰지 않는 곳:** 구현과 테스트 작성은 계획 맥락이 그대로 필요하다. 결정 기록은 사용자 원문을 옮기는 일이라 독립성이 필요 없다. 다만 큰 코드베이스에서 기존 함수 찾기(원칙 5)나 공식 문서 여러 개 확인(원칙 8)은 메인 컨텍스트를 아끼려고 탐색용 서브에이전트에 맡겨도 된다. 이때도 결과는 위치·인용만 받는다.

## 횟수 상한

상한에 닿으면 같은 검토를 다시 띄우지 않는다.

| 검토 | 상한 | 상한에 닿은 뒤 |
|---|---|---|
| 결함 주입 | 작업 단위당 1회, 결함 최대 5개 | 추가한 테스트가 결함을 잡는지는 메인이 그 결함만 다시 넣어 확인한다 |
| 보고서 감사 | 보고서당 2회(최초 1회 + 수정 후 재감사 1회) | 남은 지적은 메인이 자체 점검으로 처리하고, 해결하지 못한 것은 "확인하지 못한 것"으로 옮긴다 |
| 계획 검토 | 요청 1번에 1회 | 다시 원하면 사용자가 다시 요청한다 |

보고서 감사에서 캡처는 ✅ 시나리오의 것만 연다. 이미지 하나하나가 토큰을 쓴다.

## 모델

계획 검토·보고서 감사는 체크리스트 판정이라 가벼운 모델로 충분하다. 결함 주입은 코드를 이해해야 하므로 메인과 같은 급을 쓴다.

## 공통 규칙

- 지시문은 아래 템플릿을 **그대로** 쓰고 `{ }` 안의 경로·명령만 바꾼다. 무엇을 고쳤는지, 어디가 걱정되는지 같은 설명을 덧붙이지 않는다. "재시도 로직을 고쳤으니 그 부분 봐 줘" 한 문장으로도 서브에이전트는 작성자의 눈으로 보게 된다.
- 경로는 넘기되 내용을 요약해서 넘기지 않는다. 서브에이전트가 파일을 직접 읽는다.
- 모든 지시문 맨 앞에 **보안 규칙 블록**을 넣는다. 서브에이전트는 이 스킬을 읽지 않고 시작하므로, 결함 주입 중 `.env`를 출력하거나 키가 든 오류 메시지를 그대로 붙일 수 있다.
- 돌아온 결과는 요약하지 않고 원문 그대로 붙인다: 계획 검토 → 사용자에게 보여 주는 계획 아래, 결함 주입 → 검증 보고서의 "일부러 깨뜨리기" 표, 보고서 감사 → 검증 보고서의 "독립 감사 결과" 절. 반영 여부는 지적마다 판단하되, 반영하지 않은 지적도 지우지 않고 이유를 적는다.
- 같은 결과물을 다시 검토할 때는 새 서브에이전트를 띄운다(상한 안에서). 이전 지적을 아는 검토자는 "그게 고쳐졌나"만 본다.

### 보안 규칙 블록 (모든 지시문 맨 앞에)

```text
[보안 규칙 — 반드시 지킨다]
- .env, 비밀 설정 파일, 환경 변수의 값을 출력하거나 결과에 적지 않는다. 필요하면 존재 여부만 확인한다.
- 명령 출력이나 오류 메시지에 API 키·토큰·비밀번호·이메일 주소가 보이면 결과에 옮기지 않고 "****"로 가린다.
- 외부 서비스로 요청을 보내지 않는다. 네트워크가 필요한 테스트는 실행하지 말고 "실행하지 않음"으로 보고한다.
- 화면 캡처에 비밀값이나 개인 식별 정보가 보이면 그 사실만 보고하고 내용은 옮기지 않는다.
```

## 1. 계획 검토

- **언제:** 사용자가 요청할 때만(예: "계획 검토해줘", "서브에이전트로 계획 봐줘"). 작업이 커도 자동으로 돌리지 않는다. 요청받으면 계획을 확정하기 전에 돌린다. 요청 1번에 1회만 돌린다.
- **모델:** 가벼운 모델로 충분.

```text
{보안 규칙 블록}

너는 코드 변경 계획의 검토자다. 이 계획을 누가 왜 이렇게 세웠는지는 모른다. 아래 두 자료만 보고 판정한다.

- 사용자 요청 원문: {요청 원문 파일 경로 또는 원문 그대로}
- 계획서: {계획서 파일 경로}
- 확인된 제약: {제약 목록 — 없으면 "없음"}

다음을 하나씩 확인하고, 문제가 있는 항목만 보고한다.
1. 요청의 모든 항목이 계획의 "변경 내용"에 대응되는가. 빠진 항목을 요청 원문의 문장으로 인용한다.
2. 완료 기준이 테스트·캡처·명령 출력으로 확인할 수 있는 형태인가. "잘 동작한다"처럼 확인할 수 없는 기준을 인용한다.
3. 경계 상황이 빠지지 않았는가: 빈 값, 값 없음(수동 실행 등), 중복 실행, 부분 실패, 잘못된 자격 증명, 경계 시각.
4. 근거를 댈 수 없는 항목이 있는가. 근거는 요청 항목, 지금 두 곳 이상에 있는 중복, 관찰된 문제(로그·재현·측정), 확인된 제약 네 가지뿐이다. 특히: 요청에 없는 기능, 구현체가 하나뿐인 추상화, 기본값 말고 쓰는 곳이 없는 옵션, 그대로 부르기만 하는 래퍼, 측정된 문제 없이 넣은 캐시·비동기·재시도.
5. "현재 상태"에 읽고 확인하지 않은 것으로 보이는 가정이 있는가.
6. 사용자가 골라야 할 결정이 "결정이 필요한 것"에 빠져 있지 않은가.

출력 형식:
| # | 확인 항목 | 지적 | 근거(인용) | 심각도(높음/중간/낮음) |
문제가 없으면 "지적 없음"과 확인한 항목 번호만 적는다. 계획을 고쳐 쓰지 않는다.
```

- **붙이는 곳:** 사용자에게 보여 주는 계획 바로 아래 "계획 검토 결과" 절. 지적마다 "반영함 / 반영하지 않음(이유)"을 적는다. 의도적으로 뺀 범위를 누락으로 지적했으면 반영하지 않고 그 이유를 적는다. 반영 여부가 결과를 바꾸면 사용자에게 묻는다.

## 2. 결함 주입

- **언제:** 원칙 2의 작업 단위마다 최대 한 번. 그 단위에 "높음" 테스트가 있고 처음 모두 통과했을 때.
- **과하게 하지 않는다.** 테스트를 과하게 만들지 않는 것(원칙 4)과 같은 이유다. 검토 부담만 커지고, 놓친 결함마다 테스트를 붙이면 약한 테스트가 늘어난다. 그래서 "높음" 범주에만, 범주당 1개, 단위당 최대 5개 넣고, 행동이 바뀌지 않는 "동등" 결함에는 테스트를 만들지 않는다.
- **원본은 건드리지 않는다.** git이 있으면 커밋된 깨끗한 작업 트리에서 돌리고 끝난 뒤 `git diff`가 비어 있는지 확인한다. git이 없으면 처음부터 임시 복사본(비밀 파일 제외)에서만 돌린다.
- **모델:** 메인과 같은 급. 코드를 이해하고 그럴듯한 결함을 골라야 한다.
- **시작 전 메인이 할 일:**
  1. **대상 범위를 정한다.** 넘기는 것은 파일·함수 이름뿐이다.
     - git이 있으면: 단위 시작 커밋 기준 `git diff --stat`과 바뀐 함수.
     - git이 없으면: 단위 구현을 시작할 때 떠 둔 스냅숏과 비교한다.
     - 스냅숏도 없으면: 계획의 "변경 내용"과 실제로 고친 함수 목록. 보고서에 "범위: 계획 기준(diff 미확인)"이라고 적는다.
  2. **작업 장소를 정한다.** git이 있으면 `git status`가 깨끗한지 확인한다(아니면 커밋). git이 없으면 프로젝트를 임시 폴더로 복사하고 그 경로를 작업 디렉터리로 넘긴다.
  3. **관련 테스트만 도는 실행 명령을 정한다.** 전체 테스트를 매번 돌리지 않는다.

  git이 없을 때의 스냅숏과 복사본 예시(경로는 프로젝트에 맞게 바꾼다):
  ```bash
  # 단위 구현을 시작할 때: 계획의 "변경 내용" 파일만, 프로젝트 밖에 스냅숏
  SNAP=$(mktemp -d)
  rsync -R src/export.py src/http_client.py "$SNAP"/
  # 단위가 끝난 뒤: 바뀐 범위 확인
  for f in src/export.py src/http_client.py; do diff -u "$SNAP/$f" "$f"; done
  # 결함 주입용 복사본: 비밀 파일 제외
  WORK=$(mktemp -d)
  rsync -a --exclude '.env*' --exclude '*.pem' --exclude '*secret*' ./ "$WORK"/
  ```

```text
{보안 규칙 블록}

너는 테스트의 빈틈을 찾는 검토자다. 테스트를 쓴 사람의 의도는 모른다. 코드와 테스트만 보고 판단한다.

- 대상 범위: {이번 작업 단위에서 바뀐 파일:함수 목록} — 이 범위 밖에는 결함을 넣지 않는다
- 관련 테스트: {테스트 파일 경로 목록}
- 테스트 실행 명령: {예: pytest tests/test_export.py -q}
- 작업 디렉터리: {경로}

절차:
1. 테스트 실행 명령을 한 번 돌려 모두 통과하는지 확인한다. 실패가 있으면 여기서 멈추고 실패 출력만 보고한다.
2. 대상 범위 안에서 아래 범주에 해당하는 코드를 찾고, "실제로 일어날 법한" 결함을 **범주당 1개, 전체 최대 5개** 고른다.
   범주: 데이터 손실·중복(멱등성), 비밀값 마스킹 누락, 예외 타입·재시도/실패 판단 변경, 부분 실패 처리.
   범위 안에 이 범주의 코드가 없으면 결함을 넣지 않고 "대상 없음"으로 보고하고 끝낸다.
   문법 오류나 import 삭제처럼 아무 테스트나 실패시키는 결함, 행동이 바뀌지 않는 결함은 고르지 않는다.
3. 결함을 하나씩 넣고 → 테스트를 돌리고 → 결과를 기록하고 → 원래대로 되돌린다. 한 번에 하나만 넣는다. 테스트 출력은 옮기지 말고 실패한 테스트 이름만 기록한다. 넣고 보니 행동이 바뀌지 않는 결함이면 "동등"으로 기록한다.
4. 끝나면 원본이 그대로인지 확인하고 결과를 보고한다(git이 있으면 `git diff`가 비어 있음, 복사본에서 했으면 "복사본에서 수행").

출력 형식:
| # | 범주 | 파일:줄 | 넣은 결함(한 줄) | 실패한 테스트(없으면 "없음") | 잡혔나(잡힘·놓침·동등) |
마지막에:
- 잡히지 않은 결함마다: 어떤 입력·상황에서 문제가 되는지 한 줄, 그것을 잡을 테스트 이름 제안 한 줄.
- 원본 복구 확인 결과.
코드나 테스트를 고쳐서 남기지 않는다.
```

- **붙이는 곳:** 검증 보고서의 "일부러 깨뜨리기" 표. "수행: 서브에이전트(독립)"과 원본 복구 확인 결과를 함께 적는다.
- **결과 처리:** 잡히지 않은 결함은 테스트 우선순위표(testing.md §1)에 올려 순위를 매긴다. "높음"이면 테스트를 추가하고, 그 결함을 다시 넣어 새 테스트가 실패하는지 메인이 확인한다. 그 외는 보류 목록으로 사용자에게 알린다. "동등"은 테스트를 만들지 않는다. 놓친 결함의 코드가 아무 근거도 지키지 않아 지워도 되는 코드로 보이면, 테스트를 붙이지 말고 원칙 11로 삭제를 검토해 사용자에게 묻는다. 같은 단위에 결함 주입을 다시 돌리지 않는다.
- **끝난 뒤 메인이 할 일:** git이면 `git diff`가 비어 있는지 직접 한 번 더 확인한다. 복사본에서 했으면 임시 폴더를 지운다.

## 3. 보고서 감사

- **언제:** 검증 보고서를 만든 작업. 사용자에게 보고하기 전.
- **모델:** 가벼운 모델로 충분. 단, 캡처 이미지를 열어 볼 수 있어야 한다.

```text
{보안 규칙 블록}

너는 검증 보고서의 감사자다. 이 기능을 누가 어떻게 만들었는지는 모른다. 보고서와 증거 파일만 보고 판정한다.

- 보고서: {docs/verification/YYYY-MM-DD_기능.md}
- 캡처 폴더: {docs/verification/captures/}

다음을 하나씩 확인하고, 문제가 있는 항목만 보고한다.
1. ✅인 시나리오마다 증거 링크가 있는가.
2. 모든 링크(캡처, 코드, 결정 기록)가 실제 파일을 가리키는가. 직접 존재를 확인한다.
3. ✅인 시나리오의 캡처를 직접 열었을 때(✅가 아닌 캡처는 열지 않는다), 파일 이름과 보고서의 "관찰" 칸이 말하는 내용이 화면에 실제로 보이는가. 보이지 않으면 무엇이 보이는지 적는다.
4. 캡처나 보고서 본문에 API 키·토큰·비밀번호·개인 이메일 주소가 보이는가. (보이면 위치만 적고 값은 옮기지 않는다.)
5. "관찰" 칸이 "기대" 칸을 그대로 복사한 것처럼 보이는 시나리오가 있는가.
6. 사람만 확인할 수 있는 단계(메일 수신 등)가 ✅인데 사용자 관찰 원문이 없는 경우가 있는가.
7. "확인하지 못한 것" 절이 비어 있다면, 보고서 안에 실제로는 확인하지 못한 것으로 보이는 항목이 있는가.
8. 캡처 파일 이름이 `{기능}_{시나리오}_{결과}.png` 규칙을 따르는가.

출력 형식:
| # | 확인 항목 | 대상(시나리오 번호·파일) | 지적 | 근거 |
문제가 없으면 "지적 없음"과 확인한 항목 번호만 적는다. 보고서를 고쳐 쓰지 않는다.
```

- **붙이는 곳:** 검증 보고서의 "독립 감사 결과" 절에 원문 그대로. 지적마다 "지적별 조치" 표에 반영 여부와 이유를 적는다.
- **결과 처리:** 증거가 없는 ✅는 다시 확인해서 증거를 붙이거나, ✅를 내리고 "확인하지 못한 것"으로 옮긴다. 비밀값이 보이는 캡처는 원칙 1에 따라 다시 찍는다. 보고서를 크게 고쳤으면 새 서브에이전트로 한 번 더 감사한다. 재감사는 한 번까지다. 그 뒤에도 남은 지적은 메인이 자체 점검으로 처리하고, 해결하지 못한 것은 "확인하지 못한 것"으로 옮긴다.

## 서브에이전트 도구가 없을 때

메인 에이전트가 같은 체크리스트로 직접 점검한다. 결과를 붙인 자리에 "수행: 자체 점검 — 독립 검증 아님"이라고 적어, 나중에 읽는 사람이 독립 검증을 거치지 않았다는 사실을 알 수 있게 한다.
