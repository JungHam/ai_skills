# 결정 기록 서식

SKILL.md 원칙 9의 상세판. 사용자가 여러 선택지 중 하나를 골라야 할 때 쓴다.

## 흐름

1. 선택지를 제시할 때 `docs/decisions/YYYY-MM-DD_{주제}.md`를 `상태: 결정 대기`로 만든다. "결정" 절은 비워 둔다.
2. 대화에서는 원칙 8의 대안 표와 함께 이 문서 링크를 준다.
3. 사용자가 고르면 "결정" 절을 채우고 상태를 `결정됨`으로 바꾼다.
4. 구현·검증이 끝나면 "관련 증거"에 검증 보고서·테스트·커밋 링크를 단다. 검증 보고서에서도 이 문서로 링크한다.
5. 나중에 결정을 뒤집으면 새 문서를 만들고, 이 문서는 `상태: 대체됨 → [새 문서](...)`로만 바꾼다.

## 템플릿

```markdown
# 결정: {무엇을 정했나, 한 줄}

- 상태: 결정 대기 | 결정됨 | 대체됨 → [새 문서](...)
- 날짜: 제시 YYYY-MM-DD / 결정 YYYY-MM-DD
- 결정한 사람: 사용자
- 관련 작업: (작업 단위·계획 이름, 예: 화면 E2E 검증)

## 배경
왜 이 결정이 필요해졌나. 관찰한 사실(로그·재현 결과·문서 인용)과 추론을 구분해서 쓴다.

## 제약
이 상황에서 대안을 고르는 기준이 되는 조건. (예: 운영 인원, 예산·디스크 한도, 기존 API를 바꿀 수 있는가)

## 선택지

| 대안 | 방법 | 장점 | 단점 | 이 상황에 맞나 |
|---|---|---|---|---|
| A | ... | ... | ... | ... |
| B | ... | ... | ... | ... |

- 제안 시 추천: A — (추천 이유)

## 결정
- 선택: A
- 사용자 원문: "A로 가자."
- 선택 이유: (사용자가 말한 이유를 원문으로. 말하지 않았으면 "이유는 밝히지 않음")
- 추천과 같은가: 같음 | 다름 (다르면 무엇이 달랐는지)

## 감수한 단점
고른 대안의 단점 중 받아들이기로 한 것.

## 다시 볼 조건
이 조건이 생기면 결정을 다시 검토한다.

## 관련 증거
- 검증 보고서, 테스트 이름, 캡처, 커밋 링크
```

## 작성 규칙

- 선택지 표는 대화에서 제시한 표와 내용이 같아야 한다. 결정한 뒤에 표를 고쳐 고른 대안을 더 좋아 보이게 만들지 않는다.
- "사용자 원문"은 고치지 않는다. 오타도 그대로 둔다.
- 사실(실측·문서)과 추론을 섞지 않는다. 확인하지 않은 것은 "추정"이라고 쓴다.
- 비밀값·식별 정보는 원칙 1에 따라 넣지 않는다.

## 예시: 웹 폼의 빠른 이중 등록 방지

```markdown
# 결정: 빠른 이중 등록을 화면에서 저장 중 확인 + 버튼 잠금으로 막는다

- 상태: 결정됨
- 날짜: 제시 2026-10-30 / 결정 2026-10-30
- 결정한 사람: 사용자
- 관련 작업: todo 앱 화면 E2E 검증 후속 수정

## 배경
- 관찰: 등록 버튼을 더블클릭하면 서버·화면에 같은 todo가 2개 생긴다(브라우저 자동화로 재현, 직전 수정 이전 코드에서도 동일).
- 원인: 저장 중인지 확인하지 않아 한 번의 등록 의도에 요청이 2개 나간다.

## 제약
- 같은 제목을 일부러 다시 등록하는 것은 허용해야 한다(중복 허용 여부는 초기 설계에서 보류).
- 테스트용 앱이라 API 형식 변경 비용을 줄이고 싶다.

## 선택지
| 대안 | 방법 | 장점 | 단점 | 이 상황에 맞나 |
|---|---|---|---|---|
| A1 | 저장 중 등록 무시 + 버튼 잠금, 입력칸은 열어 둠 | 원인을 그 자리에서 막음, 의도한 중복 허용 | 저장 중 다른 제목 Enter는 무시됨(글자는 남음) | 추천 |
| A2 | 같은 제목이 저장 중일 때만 무시 | 다른 제목은 즉시 등록 | 상태 관리 복잡, 저장 중 표시 없음 | 이득 적음 |
| B | 서버가 중복 제목 거절(409) | API 직접 호출에도 적용 | 의도한 중복까지 막음 | 비추천 |
| C | 요청마다 멱등 키, 서버가 한 번만 처리 | 재시도까지 막는 가장 확실한 방법 | API·서버 저장 변경 | 과함 |

- 제안 시 추천: A1 — 원인을 겨냥하면서 사용자 행동과 API를 바꾸지 않는다.

## 결정
- 선택: A1
- 사용자 원문: "A1으로 가자."
- 선택 이유: 이유는 밝히지 않음
- 추천과 같은가: 같음

## 감수한 단점
- 저장 중에 다음 제목을 입력하고 누른 Enter는 무시된다. 입력한 글자는 남아 있어 다시 누르면 된다.

## 다시 볼 조건
- 저장이 체감될 만큼 느려지면(예: 1초 이상) A2 재검토.
- 화면 밖에서 API를 직접 호출하는 클라이언트가 생기면 C 검토.

## 관련 증거
- 검증 보고서: docs/verification/2026-10-30_todo_app_ui.md (시나리오 8~12)
- 테스트: test_double_click_submit_saves_once, test_programmatic_submit_while_saving_saves_once
```
