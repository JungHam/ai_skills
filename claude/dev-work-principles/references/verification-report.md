# 실제 동작 검증과 결과 저장

SKILL.md 원칙 3의 상세판. 단위 테스트 통과 뒤 실제 런타임에서 기능이 동작하는지 확인하고, 그 결과를 구현 단위별 폴더에 남긴다.

## 왜 실제로 돌려 보나

단위 테스트는 "내가 상상한 입력"에서만 맞다는 걸 보여 준다. 예: 예약 작업이 테스트에서는 "예약 시각" 값을 항상 받았지만, 운영 중 **수동 실행**하자 그 값이 비어 있어 실제 실행에서 깨지는 일. 웹 폼이 단위 테스트는 다 통과했지만, 저장 응답을 기다리는 사이 사용자가 입력한 글자를 지워 버리는 일.

검증 대상과 방법:
- 웹 화면: 브라우저 자동화(Playwright, Cypress 등)나 브라우저 도구로 클릭·입력을 시뮬레이션
- 모바일 앱: 시뮬레이터·에뮬레이터 화면
- 예약·배치 작업: 스케줄러의 실행 기록 화면(cron 로그, CI 작업 기록, 워크플로 도구 UI 등)과 재시도 횟수
- 알림: 실제로 받은 메일·메신저 메시지
- 파일·저장소 결과: 실행 전후 파일·행 수 비교
- CLI: 명령 출력

## 폴더 구조

구현 단위(원칙 2)마다 폴더 하나를 만든다. 한 단위의 결과는 그 폴더만 열면 다 보인다.

```
docs/verification/
├── 2026-11-05_order_export_u1_csv_convert/
│   └── report.md
├── 2026-11-05_order_export_u2_download_api/
│   └── report.md
└── 2026-11-06_order_export_u3_download_button/
    ├── report.md
    ├── captures/
    │   ├── download_button_click_file_saved.png
    │   └── download_button_empty_orders_message_shown.png
    ├── fault-injection.md
    └── audit.md
```

- 폴더 이름: `YYYY-MM-DD_{기능}_{단위}`. 소문자·스네이크 케이스. 날짜는 단위 작업을 시작한 날이다. 날짜가 앞에 있어 이름순이 곧 작업 순서다.
- 쪼개지 않은 작업은 작업 전체가 한 단위다: `YYYY-MM-DD_{기능}`.
- `captures/`는 캡처가 있을 때만, `fault-injection.md`와 `audit.md`는 사용자가 서브에이전트 검토를 요청했을 때만 만든다.
- 원칙 7의 예외(오타·한 줄 수정)는 폴더를 만들지 않는다.
- 사용자가 저장 위치를 지정했으면 그 위치를 따르고, 그 안에서 단위별 폴더를 만든다.

## 캡처

- 캡처는 **검증한 기능이 이름에 드러나게** 짓는다: `{기능}_{시나리오}_{결과}.png`, 소문자·스네이크 케이스.
  - 좋음: `todo_add_two_then_listed.png`, `retry_job_4_attempts_then_failed.png`, `daily_import_rerun_same_row_count.png`, `failure_email_received_masked_key.png`
  - 나쁨: `screenshot1.png`, `캡처.png`, `image (3).png`
- 완료 기준 하나에 캡처 하나면 충분하다. 같은 화면을 시나리오마다 다시 찍지 않는다.
- 실패 경로도 캡처한다. "정상 동작"만큼 "의도대로 실패함"이 중요하다.
- 캡처는 보고서에서 **상대 경로 링크**로 건다. 이미지 임베드(`![]()`)를 함께 써도 되지만 링크는 반드시 둔다.

| 대상 | 방법 |
|---|---|
| 웹 UI(내 앱, 관리 콘솔, 워크플로 도구 화면) | 브라우저 자동화나 브라우저 도구로 이동 → 클릭·입력 시뮬레이션 → 스크린샷. 자동화 테스트라면 확인(assert)을 마친 **뒤에** 저장 |
| 모바일 앱 | 시뮬레이터·에뮬레이터 스크린샷 |
| CLI 결과(실행 전후 파일 수, 작업 실행 기록) | 핵심 줄만 보고서에 붙이고, 필요하면 터미널 캡처 |
| 사람만 볼 수 있는 것(받은 메일·메시지) | 사용자에게 캡처를 부탁하고, 받은 파일을 규칙대로 이름 바꿔 저장 |

캡처 전 점검: 화면에 API 키, 비밀번호, 개인 이메일 주소 등이 보이면 가리거나 다른 화면을 쓴다(원칙 1).

캡처 후 점검: 캡처를 **직접 열어 보고** 이름이 말하는 내용이 실제로 보이는지 확인한다. 화면에 드러나지 않는 값(예: 입력칸의 공백)은 보고서에 따로 적는다.

## report.md 템플릿

`report.md`는 한 화면에 들어오게 쓴다. 해당 없는 절은 지운다.

```markdown
# 검증: {기능} {단위}

- 날짜: YYYY-MM-DD
- 대상 코드: [`src/alerts.py`](../../../src/alerts.py)
- 테스트: `pytest tests/test_alerts.py` — N passed
- 결정 기록: [이중 등록 방지](../../decisions/2026-10-30_double_submit_prevention.md)

## 결론
한두 문장. 완료 기준을 만족했나, 남은 문제가 있나.

## 시나리오
| # | 조건 | 기대 | 관찰 | 결과 | 증거 |
|---|---|---|---|---|---|
| 1 | 재시도 3회로 설정한 작업이 항상 실패 | 4회 시도 후 실패 처리 | 4회 시도 후 실패 처리 | ✅ | [실행 기록](captures/retry_job_4_attempts_then_failed.png) |
| 2 | 최종 실패 시 알림 | 관리자에게 메일 1통, 키 마스킹 | 메일 수신, 키 `****` 처리 | ✅ | [받은 메일](captures/failure_email_received_masked_key.png) |

## 발견한 버그
- 증상 → 원인 → 수정 → 회귀 테스트 이름 (버그당 한 줄)

## 점검
- 일부러 깨뜨리기(자체 점검 — 독립 검증 아님): 3개 모두 잡힘.
- 서브에이전트 검토를 요청받아 돌렸으면: 결함 주입 4개 중 3개 잡힘, 1개 놓침 → 테스트 추가. [원문](fault-injection.md)

## 확인하지 못한 것
- 예: 메신저 알림은 연결된 채널이 없어 확인하지 못함.
```

시나리오는 완료 기준과 실패 경로 단위로 적는다. 테스트 함수를 한 줄씩 옮기지 않는다. 실행한 명령의 전체 출력도 붙이지 않는다.

## 독립 검토 원문 파일

서브에이전트의 결과는 요약하지 않고 파일에 보존하고, `report.md`에는 위처럼 한 줄과 링크만 둔다.

- `fault-injection.md` 맨 위에 적을 것:
  - 수행: 서브에이전트(독립) | 자체 점검 — 독립 검증 아님
  - 대상 범위: `git diff` 기준 | 스냅숏 diff 기준 | 계획 기준(diff 미확인)
  - 원본 복구 확인: `git diff` 비어 있음 | (git 없음) 복사본에서 수행
  - 그 아래에 결과 표: | 일부러 넣은 결함 | 실패한 테스트 | 잡혔나(잡힘·놓침·동등) | 조치 |
- `audit.md` 맨 위에 적을 것:
  - 수행: 서브에이전트(독립) | 자체 점검 — 독립 검증 아님
  - 감사 원문(지적을 요약하지 않고 그대로)
  - 지적별 조치 표: | # | 지적 | 반영 | 조치 또는 반영하지 않은 이유 |

## 규칙

- "확인됨(✅)"은 실제로 본 것에만 쓴다. 못 본 것은 "확인하지 못한 것"에 둔다.
- 사람 눈으로만 확인할 수 있는 단계(메일 수신 등)는 사용자에게 확인을 부탁하고, 사용자가 말한 관찰 결과를 원문 그대로 적는다.
- 실패한 시나리오는 ❌로 남기고 원인과 다음 조치를 적는다. 지우지 않는다.
- 링크가 실제 파일을 가리키는지 마지막에 확인한다(`ls captures/`, 또는 보고서의 링크를 뽑아 하나씩 존재 확인).
- 보고서를 넘기기 전에 메인이 [`subagent-review.md`](subagent-review.md)의 보고서 감사 항목으로 직접 점검한다. 자기 보고서의 ✅를 판정하면 관대해지기 쉬우니, 증거 없는 ✅가 없는지 특히 본다. 서브에이전트 감사는 사용자가 요청할 때만 돌린다.
- 독립 감사의 지적은 반영하지 않았더라도 지우지 않는다. 감사 뒤 보고서를 고쳤으면 어떤 지적 때문에 무엇을 고쳤는지 `audit.md`의 "지적별 조치" 표에 남긴다.
