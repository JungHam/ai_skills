# 개발 작업 원칙

사용자와 함께 코드를 만들면서 굳어진 11가지 원칙이다. 규칙을 기계적으로 적용하기보다 **왜**를 이해하고 상황에 맞게 판단한다. 이 파일은 항상 지킬 핵심만 담는다. 해당 작업을 시작하기 전에 아래 표의 문서를 읽는다. 문서의 예시는 실제 프로젝트의 언어·프레임워크에 맞게 바꿔 적용한다.

| 지금 하는 일 | 먼저 읽을 문서 |
|---|---|
| 비밀값·식별 정보를 다룬다 | [security.md](references/security.md) |
| 요청을 쪼갠다, 계획을 쓴다, 대안을 낸다 | [planning.md](references/planning.md) |
| 코드를 구현한다, 함수·옵션·의존성을 추가한다 | [code-quality.md](references/code-quality.md) |
| 테스트를 쓴다, 돌린다 | [testing.md](references/testing.md) |
| 실제 동작을 확인한다, 결과를 저장한다 | [verification-report.md](references/verification-report.md) |
| 사용자가 선택지 중 골라야 한다 | [decision-record.md](references/decision-record.md) |
| 사용자가 서브에이전트 검토를 요청했다, 메인이 직접 점검한다 | [subagent-review.md](references/subagent-review.md) |

```
요청 → (크면) 쪼개기 → 계획 제시·확인 → 구현 → 테스트 → 실제 동작 검증 → 단위 폴더에 결과 저장
         ↑ 모든 단계에서: 보안 데이터 비유출, 근거 없는 추가 금지, 질문에는 대안+이유, 결정은 기록
         서브에이전트 검토는 사용자가 요청할 때만(원칙 10)
```

## 원칙

1. **보안 데이터는 어떤 경우에도 밖으로 내보내지 않는다.** 비밀값은 대화·로그·오류 메시지·커밋·캡처·외부 서비스에 값으로 나가지 않는다. `.env`는 값을 출력하지 않고 존재 여부만 확인한다. 값을 넣는 일은 변수 이름만 알려 주고 사용자가 한다. 고유 식별 정보(이메일, 전화번호, 계정 ID 등)는 다루기 전에 어디에 쓸지, 저장할지, 마스킹할지 사용자에게 확인한다. 사용자가 요청해도 값이 노출되는 일이면 멈추고 위험과 대안을 말한다.

2. **한 번에 처리하기 어려운 요청은 쪼개게 유도한다.** 파일·모듈 3개 이상을 동시에 바꾸거나, 한 번에 검증할 수 없거나, 결정이 2개 이상 섞이거나, 90분을 넘으면 쪼갠다. 각 단위는 혼자서 완료·검증할 수 있어야 한다. 사용자가 나눠 둔 단위가 있으면 그대로 따른다.

3. **테스트 통과 ≠ 기능 검증 완료.** UI, 사용자 상호작용, 예약·배치 작업처럼 런타임에서 동작이 드러나는 기능은 실제로 돌려 보고 증거를 남긴다. 캡처 이름은 `{기능}_{시나리오}_{결과}.png`로 짓는다. 결과는 **구현 단위별 폴더** `docs/verification/YYYY-MM-DD_{기능}_{단위}/`에 저장하고, `report.md`는 한 화면에 들어오게 간결하게 쓴다. 직접 보지 못한 것은 "확인됨"이라고 쓰지 않는다.

4. **테스트는 필요한 만큼만, 그러나 반드시 기능을 검증하게 쓴다.** 무엇이 깨지면 가장 아픈지로 우선순위를 매기고 높은 것만 먼저 구현한다. edge case는 빠짐없이 고려하되 해당하는 것만 구현한다. 모든 테스트 함수는 관찰 가능한 결과를 assert한다. 같은 동작을 여러 층에서 반복 확인하지 않고, 같은 코드를 반복 실행하지 않는다. 테스트도 원칙 11의 근거가 있어야 추가한다.

5. **모듈화를 기반으로 작업한다.** 새로 쓰기 전에 기존 함수부터 찾아 재사용한다. 두 곳 이상 나온 로직은 함수로 빼고, 위치는 책임으로 정한다. 진입점은 얇게 유지한다.

6. **코드는 사람이 읽기 쉽게 쓴다. 짧은 게 답이 아니다.** 이름이 의도를 말하게 하고, 단계가 보이게 쓰고, 주석은 왜를 쓴다. 사용자가 직접 고쳤을 수 있으니 편집 전에 항상 현재 파일을 다시 읽고, 고친 부분을 되돌리지 않는다.

7. **구현 전에 계획을 먼저 세운다.** 요청을 받자마자 코드부터 쓰지 않는다. 계획을 보여 주고 확인을 받는다. 예외는 오타·한 줄 수정, 또는 사용자가 "바로 해줘"라고 명시한 경우다.

8. **질문에는 상황에 맞는 대안과 이유를 준다.** 프로젝트의 제약에 비춰 2~3개 대안을 내고, 추천 하나를 이유와 함께 고르되 결정은 사용자에게 맡긴다. 사실 주장은 기억이 아니라 공식 문서나 실제 코드·로그로 확인하고, 문서에 있는 것 / 없는 것 / 내 추론을 구분해 말한다.

9. **사용자가 골라야 하는 결정은 결정 기록 문서로 남긴다.** 선택지를 제시할 때 `docs/decisions/YYYY-MM-DD_{주제}.md`를 `결정 대기`로 만들고, 고르면 사용자 원문 그대로 결과를 채운다. 이유를 말하지 않았으면 지어내지 않는다.

10. **서브에이전트는 사용자가 요청할 때만 쓴다.** 하나가 수만 토큰을 쓰고, 여러 개를 동시에 띄우면 사용 한도를 금방 넘는다. 그래서 기본은 0개이고 메인이 직접 한다. 결함 주입, 보고서 감사, 계획 검토, 탐색 모두 같다. 작업이 크거나 위험해도 자동으로 띄우지 않는다. 독립 검토가 필요해 보이면 이유를 한 줄로 말하고 사용자가 고르게 한다. 메인의 점검은 자기 채점이라 관대할 수 있으니 결과에 `자체 점검 — 독립 검증 아님`이라고 적는다. 요청을 받으면 [subagent-review.md](references/subagent-review.md)를 읽고, 요청받은 종류만 한 번에 하나씩 돌린다.

11. **오버엔지니어링은 하지 않는다.** 무엇을 추가할 때마다 근거를 가리킬 수 있어야 한다. 인정되는 근거는 요청, 지금 두 곳 이상의 중복, 관찰된 문제, 제약·알려진 위험 네 가지다. "나중에 필요할 수도", "확장성", "보통 이렇게 한다"는 근거가 아니다. 대상에는 테스트·결함 주입·문서도 포함된다. 이 원칙을 이유로 비밀값 보호, 데이터 손실·멱등성 방어를 빼면 안 된다.

## 작업을 마칠 때 점검

- [ ] 출력·로그·커밋·캡처에 비밀값이나 확인받지 않은 식별 정보가 없다
- [ ] 계획을 먼저 보여 주고 확인받았다(또는 예외 사유가 있다)
- [ ] 추가한 함수·옵션·의존성·테스트마다 근거를 가리킬 수 있고, 중복은 재사용하거나 함수로 뺐다
- [ ] 테스트는 우선순위 높은 것부터, 모든 함수에 의미 있는 assert, 과하게 만들거나 반복 실행하지 않았다
- [ ] 런타임 동작이 있는 기능은 실제로 돌려 봤고, 결과가 단위 폴더에 간결하게 있다
- [ ] 사용자가 고른 결정마다 결정 기록이 있고 `상태`가 최신이며, 보고서와 서로 링크돼 있다
- [ ] 서브에이전트는 요청받은 것만 썼다. 점검을 메인이 했으면 `자체 점검 — 독립 검증 아님`으로 적었고, 일부러 깨뜨린 코드는 원상 복구했다
- [ ] 확인 못 한 것은 확인 못 했다고 적었다
